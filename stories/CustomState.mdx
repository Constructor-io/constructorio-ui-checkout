# Custom State

Most checkouts carry flow-scoped state that doesn't fit in the cart, session, or step id — a gift-wrap toggle, the shipping method picked on step 2, a coupon draft, a "same as billing" checkbox. Custom state is a typed slot on the flow for exactly that.

The library persists it, restores it on resume, and exposes typed getters and setters. Use it in place of a parallel React store for anything scoped to the checkout flow.

## Under the hood

Custom state is the `TState` generic on `CheckoutFlowConfig<TState>` and `useCioCheckout<TState>()`. Internally the library calls it `integratorState` — the name appears in the API (`getIntegratorState`, `setIntegratorState`, `initialState`). Same concept, older name.

## Shape

```ts
interface CheckoutFlowConfig<TState = unknown> {
  initialState?: TState;
  // ... other config
}

interface CheckoutFlowCore<TState = unknown> {
  getIntegratorState(): TState;
  setIntegratorState(updater: (prev: TState) => TState): void;
  // ... other methods
}
```

- `initialState` — the value used if nothing hydrates from storage. Required in the type when `TState` is not `undefined`-compatible.
- `getIntegratorState()` — synchronous read of the current value.
- `setIntegratorState(updater)` — functional setter, same shape as React's `setState(prev => next)`.

## Wiring it up

```tsx
type MyCheckoutState = {
  giftWrap: boolean;
  shippingMethod: 'standard' | 'express' | null;
  couponDraft: string;
};

const initialState: MyCheckoutState = {
  giftWrap: false,
  shippingMethod: null,
  couponDraft: '',
};

<CioCheckoutProvider<'stripe', MyCheckoutState>
  provider="stripe"
  steps={[...]}
  onCreateSession={...}
  initialState={initialState}
>
  <MyCheckout />
</CioCheckoutProvider>
```

Then anywhere inside the provider:

```tsx
function ShippingPicker() {
  const flow = useCioCheckout<'stripe', MyCheckoutState>();
  const shippingMethod = flow.getIntegratorState().shippingMethod;

  return (
    <select
      value={shippingMethod ?? ''}
      onChange={(e) =>
        flow.setIntegratorState((prev) => ({
          ...prev,
          shippingMethod: e.target.value as 'standard' | 'express',
        }))
      }
    >
      <option value="standard">Standard</option>
      <option value="express">Express</option>
    </select>
  );
}
```

The generic on `useCioCheckout<'stripe', MyCheckoutState>()` matches the one passed to the provider. TypeScript cannot infer it across the context boundary, so re-assert it at each call site.

## When state changes trigger re-renders

`setIntegratorState` mutates the flow store through the same subscription mechanism as `state.currentStepId` or `cartSnapshot`. Components using `useCioCheckout()` re-render on every custom state change.

For a large custom state where granular re-renders matter, select the field you need:

```tsx
const shippingMethod = useCioCheckout<
  'stripe',
  MyCheckoutState
>().getIntegratorState().shippingMethod;
```

React bails out of the update when `shippingMethod` is referentially equal to the previous render. For heavy trees, wrap the read in `useMemo` or use a memoized selector.

## Custom state vs `metadata`

The library exposes two ways to carry extra data. They are not interchangeable.

|                  | Custom State (`integratorState`)                | `metadata` on `CheckoutFlowState`                              |
| ---------------- | ----------------------------------------------- | -------------------------------------------------------------- |
| **Type**         | Fully typed via `TState`                        | `Record<string, unknown>`                                      |
| **Access**       | `getIntegratorState()` / `setIntegratorState()` | `flow.state.metadata` (read-only from your side)               |
| **Written by**   | Your code, via `setIntegratorState`             | The library (session hooks, auth), not you                     |
| **Persisted**    | Yes                                             | Yes                                                            |
| **Intended for** | Merchant-owned flow-scoped state                | Library-internal metadata + your `initialState`-adjacent hints |

Use custom state for anything you mutate. `metadata` is a slot the library writes into and you read from.

## Custom state vs your app's Redux/Zustand store

Custom state is scoped to _this specific flow instance_. For global state that outlives checkout (user profile, cart before checkout begins, product catalog), keep it in your existing store and pass it in via props or context.

Reach for custom state when:

- The value is only meaningful during the checkout flow (gift-wrap choice on this order).
- The value should persist alongside `CheckoutFlowState` and hydrate on resume.
- Multiple steps read and write it.

Skip custom state when:

- The value is app-wide (auth token, user id).
- The value is a derived read-only projection of props (cart total).

## Persistence

Custom state lives under `CheckoutFlowState.metadata` — persisted by the configured `CheckoutStorageAdapter`, hydrated on resume. Everything in [Persistence](./?path=/docs/adapters-persistence--docs) about backend storage, encryption, and abandoned-cart recovery applies unchanged.

When renaming or restructuring `TState`, bump `storageKey` to invalidate stored entries. Otherwise a resumed flow hydrates with a shape that no longer matches the new type.

## Reading in `onCreateSession`

`onCreateSession(state)` receives `CheckoutFlowState`, not `TState`. When the session creator needs the shipping method or gift-wrap toggle, read it from the flow first:

```tsx
onCreateSession={async (state) => {
  const { shippingMethod } = flow.getIntegratorState();
  return fetch('/api/checkout-session', {
    method: 'POST',
    body: JSON.stringify({ items: state.cartSnapshot, shippingMethod }),
  }).then((r) => r.json());
}}
```

Or capture the flow via `useMemo` inside a component and close over it, depending on where the config is constructed.
