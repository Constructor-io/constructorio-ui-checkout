# Payment Providers

`<CioCheckoutProvider>` takes a required `provider` prop naming the payment
service processor (PSP) driving the checkout. The prop shapes three things at
compile time:

- The return type of `onCreateSession`
- The runtime session available via `useCioCheckout().getSession()`
- Which built-in step components can be mounted inside the provider

## Built-in providers

The library ships payment UI for Stripe, Fiserv and Shop Pay. The `provider` value
narrows `onCreateSession` and decides which built-in step can be mounted.
Mounting a built-in step inside a provider with a different `provider` prop
throws at render with a message naming both sides of the mismatch.

| `provider`  | Session type            | Step                       | Script tag added by | Charge happens in                 | Steps you declare               |
| ----------- | ----------------------- | -------------------------- | ------------------- | --------------------------------- | ------------------------------- |
| `"stripe"`  | `StripePaymentSession`  | `<CioStripePaymentStep>`   | Stripe's npm package | Stripe's widget, in the payment step | cart, payment, done            |
| `"fiserv"`  | `FiservPaymentSession`  | `<CioFiservPaymentStep>`   | The library         | Your server, after the card is captured | cart, payment, complete      |
| `"shop-pay"` | None (no `onCreateSession`) | `<CioShopPayPaymentStep>` | The library      | Shop Pay's popup, in the payment step | cart, payment, complete      |

### Stripe

Passing `provider="stripe"` narrows `onCreateSession` to return a
`StripePaymentSession` (`{ clientSecret, publishableKey }`) and allows
`<CioStripePaymentStep>` to be mounted.

```tsx
<CioCheckoutProvider
  provider="stripe"
  steps={[{ id: 'cart' }, { id: PAYMENT_STEP }, { id: 'done' }]}
  onCreateSession={async () => {
    const res = await fetch('/api/checkout-session', { method: 'POST' });
    return res.json(); // typed as StripePaymentSession
  }}
>
  <CioCheckoutStep id={PAYMENT_STEP}>
    <CioStripePaymentStep uiMode="form" />
  </CioCheckoutStep>
</CioCheckoutProvider>
```

### Fiserv

Passing `provider="fiserv"` narrows `onCreateSession` to return a
`FiservPaymentSession` and allows `<CioFiservPaymentStep>` to be mounted.
Your server signs Fiserv's credentials call and returns the result plus
`apiKey`, `merchantId`, `terminalId` and `environment`. See
[CioFiservPaymentStep](./?path=/docs/components-utilities-ciofiservpaymentstep--docs)
for the field list.

Fiserv's hosted fields store the card in a PaymentSession. They do not charge
it. The charge is a second call your server makes with the session id, so the
flow needs one more step than Stripe: a `<CioFulfillmentStep>` whose
`onFulfill` calls your charge route. The step reads the session id with
`useCioCheckout()`, so it lives in a component under the provider.

```tsx
function Complete() {
  const flow = useCioCheckout<'fiserv'>();
  return (
    <CioFulfillmentStep
      onFulfill={async () => {
        const res = await fetch('/api/fiserv/charge', {
          method: 'POST',
          headers: { 'Content-Type': 'application/json' },
          // Your server prices the order itself. Send only what it needs to find it.
          body: JSON.stringify({ sessionId: flow.getSession()?.sessionId }),
        });
        return res.json(); // { success, message }
      }}
    />
  );
}

<CioCheckoutProvider
  provider="fiserv"
  steps={[{ id: 'cart' }, { id: PAYMENT_STEP }, { id: 'complete' }]}
  onCreateSession={async () => {
    const res = await fetch('/api/fiserv/session', { method: 'POST' });
    return res.json(); // typed as FiservPaymentSession
  }}
>
  <CioCheckoutStep id={PAYMENT_STEP}>
    <CioFiservPaymentStep amount="$49.99" frameAncestors={[location.origin]} />
  </CioCheckoutStep>
  <CioCheckoutStep id="complete">
    <Complete />
  </CioCheckoutStep>
</CioCheckoutProvider>
```

Fiserv spends a session on its first use. After a failed charge, call
`flow.recreate()` and send the shopper back to the payment step so they enter
the card again. The `/fiserv` flow in `examples/checkout-test-server` shows
this, with the server routes in `server/fiserv.ts`.

### Shop Pay

Passing `provider="shop-pay"` allows `<CioShopPayPaymentStep>` to be mounted.
Leave out `onCreateSession`: Shop Pay starts its own session when the shopper
clicks the button. The step takes three callbacks instead, one per server
route: session create, submit, and receipt lookup. See
[CioShopPayPaymentStep](./?path=/docs/components-utilities-cioshoppaypaymentstep--docs)
for what each one returns.

The popup collects the address, shipping and card, and charges inside the
popup, so the flow needs no fulfillment step. Shopify creates the order after
the popup closes. The step polls the receipt and only calls `flow.next()` once
it is `completed`.

```tsx
<CioCheckoutProvider
  provider="shop-pay"
  steps={[{ id: 'cart' }, { id: PAYMENT_STEP }, { id: 'complete' }]}
>
  <CioCheckoutStep id={PAYMENT_STEP}>
    <CioShopPayPaymentStep
      shopId={SHOP_ID}
      clientId={CLIENT_ID}
      paymentRequest={toPaymentRequest(cart)}
      onSessionRequest={createShopPaySession}
      onSubmitPayment={submitShopPayPayment}
      onCheckReceipt={checkShopPayReceipt}
    />
  </CioCheckoutStep>
</CioCheckoutProvider>
```

Shop Pay Wallet is for stores that do not use Shopify's own checkout. The
button only renders on the store's allowed origins, so a PR preview or this
Storybook shows nothing. The `/shop-pay` flow in
`examples/checkout-test-server` runs on localhost, with the server routes in
`server/shop-pay.ts`.

Shop Pay references:

- [Sessions and events](https://shopify.dev/docs/api/commerce-components/pay/sessions-and-events)
- [Troubleshooting guide](https://shopify.dev/docs/api/commerce-components/pay/troubleshooting-guide)

## Custom providers

`provider` accepts any string. For an unofficial PSP (Adyen, Braintree,
in-house, sandbox), you own the payment UI and drive the flow through
`useCioCheckout()`:

```tsx
<CioCheckoutProvider
  provider="my-psp"
  steps={[{ id: 'cart' }, { id: PAYMENT_STEP }, { id: 'done' }]}
  onCreateSession={async () => {
    const res = await fetch('/api/my-psp-session', { method: 'POST' });
    return res.json();
  }}
>
  <CioCheckoutStep id={PAYMENT_STEP}>
    <MyPspStep />
  </CioCheckoutStep>
</CioCheckoutProvider>
```

Use `useCioCheckoutSession()` inside your payment step to create the session
when the shopper reaches it. See
[Sessions](./?path=/docs/guides-sessions--docs#bootstrapping-the-session-in-a-step).

If your PSP creates its session inside its own widget, as Shop Pay does, leave out
`onCreateSession`. The flow then marks the session `active` with no session
object.

Without further typing, the session is inferred as `BasePaymentSession`
(`{ sessionId?: string }`). Read it out via `flow.getSession()` and cast at
the boundary, or register a strongly-typed shape via module augmentation:

```ts
import type { BasePaymentSession } from '@constructor-io/constructorio-ui-checkout';

interface MyPspSession extends BasePaymentSession {
  approvalToken: string;
  merchantId: string;
}

declare module '@constructor-io/constructorio-ui-checkout' {
  interface PaymentSessionMap {
    'my-psp': MyPspSession;
  }
}
```

Once the map is augmented, every `<CioCheckoutProvider provider="my-psp">`,
`useCioCheckout<'my-psp'>()`, and `createCheckoutFlow<'my-psp'>()` call
resolves the session type to `MyPspSession` — full autocomplete on
`session.approvalToken` and `session.merchantId`, and a compile-time error if
`onCreateSession` returns the wrong shape.

## Session ID resolution

`sessionId` is optional on `BasePaymentSession` because Stripe's client secret
already encodes one. The library resolves it in this order:

1. `session.sessionId` when set.
2. For `provider="stripe"`, the prefix extracted from `session.clientSecret`
   (matches Stripe's `cs_test_…_secret_…` shape).
3. `null` otherwise.

For a custom PSP where you want observability events (`session.created`,
`session.updated`, `session.recreated`) to include a session identifier,
return it explicitly on `sessionId`.
