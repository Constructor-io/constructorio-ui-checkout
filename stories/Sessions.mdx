# Sessions

A Stripe session is what the flow creates to render the payment surface. It carries a `clientSecret` (identifies the session), a `publishableKey` (drives `loadStripe`), and a status the flow tracks in `state.sessionStatus`.

Most checkout bugs stem from misunderstanding the interaction between flow state, session state, and network state. This page walks through all three.

## Full example

End-to-end wiring with create, update, expiry, error handling, and analytics — the shape most production integrations settle on:

```tsx
import {
  CioCheckoutProvider,
  CioCheckoutStep,
  CioStripePaymentStep,
  PAYMENT_STEP,
  useCioCheckout,
} from '@constructor-io/constructorio-ui-checkout';
import { getCart, getCartId } from './lib/cart';
import { getAuthToken } from './lib/auth';

function CheckoutApp() {
  const onCreateSession = async () => {
    const res = await fetch('/api/checkout/session', {
      method: 'POST',
      headers: {
        Authorization: `Bearer ${getAuthToken()}`,
        'Idempotency-Key': getCartId(),
      },
      body: JSON.stringify({ cart_id: getCartId() }),
    });
    if (!res.ok) throw new Error(`Session create failed: ${res.status}`);
    return res.json(); // { clientSecret, publishableKey }
  };

  const onUpdateSession = async (patch) => {
    const res = await fetch('/api/checkout/session', {
      method: 'PATCH',
      body: JSON.stringify(patch), // { items?, metadata?, reason? }
    });
    if (!res.ok) throw new Error(`Session update failed: ${res.status}`);
    return res.json();
  };

  return (
    <CioCheckoutProvider
      provider="stripe"
      steps={[
        { id: 'cart', path: '/cart' },
        { id: PAYMENT_STEP, path: '/checkout/payment' },
        { id: 'done', path: '/order/confirmed' },
      ]}
      onCreateSession={onCreateSession}
      onUpdateSession={onUpdateSession}
      cart={getCart()}
      onEvent={(event) => {
        switch (event.type) {
          case 'session.created':
            analytics.track('checkout.session.created', {
              sessionId: event.sessionId,
            });
            break;
          case 'session.updated':
            analytics.track('checkout.session.updated', {
              reason: event.reason,
              diff: event.diff,
            });
            break;
          case 'session.expired':
            analytics.track('checkout.session.expired');
            break;
          case 'session.recreated':
            analytics.track('checkout.session.recreated', {
              oldSessionId: event.oldSessionId,
              newSessionId: event.newSessionId,
            });
            break;
          case 'error':
            analytics.track('checkout.error', {
              source: event.source,
              message: event.error.message,
            });
            break;
        }
      }}
    >
      <CioCheckoutStep id={PAYMENT_STEP}>
        <CioStripePaymentStep onError={(err) => reportToSentry(err)} />
      </CioCheckoutStep>
    </CioCheckoutProvider>
  );
}
```

That is a complete wiring. The sections below unpack each piece.

## Session status

`state.sessionStatus` is a discriminated string:

- **`idle`** — no session yet. Set on init and after `reset()`, `clearState()`, or `recreate()`.
- **`creating`** — `onCreateSession` is in flight.
- **`active`** — a session exists and is usable for payment.
- **`expired`** — the session was live but is no longer valid (Stripe reported expiry or `markExpired()` was called).
- **`error`** — `onCreateSession` rejected or returned an invalid shape. Retry with `recreate()`.

The library drives every transition; merchant code does not:

```
idle ─(createSession)→ creating ──(success)→ active
                            │
                            └──(reject)→ error ──(recreate)→ creating → ...

active ──(Stripe reports expired / markExpired())→ expired ──(recreate)→ creating → ...
```

Never write to `sessionStatus` directly. Call the methods; the status updates.

## `onCreateSession` contract

The library calls `onCreateSession(state)` with the current `CheckoutFlowState` (cart, metadata, etc.). Return a `Promise` that resolves with:

```ts
{
  clientSecret: string,      // Stripe checkout session client secret
  publishableKey: string,    // your Stripe publishable key
}
```

Reject the promise on failure. The library validates the shape — if `clientSecret` or `publishableKey` is not a string, the resolution is treated as a rejection.

```tsx
const onCreateSession = async () => {
  const res = await fetch('/api/checkout/session', {
    method: 'POST',
    body: JSON.stringify({ items: getCart() }),
  });
  if (!res.ok) throw new Error(`Session create failed: ${res.status}`);
  return res.json(); // must be { clientSecret, publishableKey }
};
```

## `onUpdateSession` contract

Optional. Called whenever `updateSession()` or `syncCart()` fires. Same shape in and out; typical use is pushing updated cart items back to Stripe.

```tsx
const onUpdateSession = async (patch) => {
  const res = await fetch('/api/checkout/session', {
    method: 'PATCH',
    body: JSON.stringify(patch), // { items?, metadata?, reason? }
  });
  return res.json(); // must return { clientSecret, publishableKey }
};
```

Without an `onUpdateSession`, calls to `updateSession()` or `syncCart()` after session creation emit an error event.

## Handling expiry

Two ways a session can expire:

**Stripe reports it.** `CioStripePaymentStep` catches this and calls `flow.markExpired()` automatically — no wiring required. Merchant code watches `sessionStatus === 'expired'` when it wants to render its own recovery UI.

**Detected externally** (e.g. a server-pushed WebSocket event). Call `flow.markExpired()`. It clears the in-memory session, sets status to `expired`, and emits `session.expired`.

Either way, recovery is one call:

```tsx
await flow.recreate();
```

`recreate()` invalidates the old session, runs `onCreateSession` again with the _current_ state (so any cart mutations since expiry are included), and emits `session.recreated` with both old and new session IDs — useful when analytics is keyed by session id.

## Handling creation errors

`CioStripePaymentStep` handles this out of the box:

- When `sessionStatus === 'error'`, it renders an error state with a Retry button that calls `flow.recreate()`.
- It fires `onError(err)` once on transition into `error`; subsequent renders do not refire (tracked via a ref).

For custom recovery UI, render conditionally on `sessionStatus`:

```tsx
function MyCustomStripePane() {
  const flow = useCioCheckout();
  if (flow.state.sessionStatus === 'error') {
    return (
      <MyErrorBanner
        onRetry={() => flow.recreate()}
        message="Couldn't prepare checkout"
      />
    );
  }
  if (flow.state.sessionStatus === 'creating' || !flow.getSession()) {
    return <MySkeleton />;
  }
  return <CioStripePaymentStep />;
}
```

## Error events

All errors emit through `onEvent` (and through `CioCheckoutProvider`'s error listener). The event carries a `source` to switch on:

- **`session.create`** — `onCreateSession` rejected or returned invalid data.
- **`session.update`** — `onUpdateSession` rejected or returned invalid data.
- **`session.recover`** — recovery attempt during hydration failed.
- **`storage`** — storage adapter's save/load/clear threw or rejected.
- **`router`** — `router.push` / `router.getCurrentPath` threw, or a `path` was refused as unsafe.
- **`guard`** — a step guard threw (rejections count as "guard failed", not error).
- **`authenticate`** — `authenticate` callback rejected or returned `null`.

```tsx
onEvent: (event) => {
  if (event.type === 'error') {
    analytics.track('checkout.error', {
      source: event.source,
      message: event.error.message,
    });
    // For `session.create` errors, `CioStripePaymentStep` shows a Retry
    // button that calls `flow.recreate()`. For other sources, wire your
    // own retry (e.g. `flow.recreate()`, `flow.syncCart(...)`).
  }
};
```

## Late-response protection

`onCreateSession` and `onUpdateSession` are network calls. When the caller invokes `reset()`, `markExpired()`, `recreate()`, or `destroy()` while a request is in flight, the library discards the stale response — an invalidated session cannot be resurrected.

In practice: if the server takes 5 seconds to return a session and the user closes the modal after 2 seconds, the eventual response is dropped. No cancellation logic required on the caller side.

## Idempotency

Two protections against double-charging if `onCreateSession` runs twice:

1. **The flow coalesces concurrent creates.** Multiple simultaneous `createSession()` calls return the same in-flight promise. Only one HTTP request goes out.
2. **Send an idempotency key server-side as well.** Stripe supports this natively. Use a stable **pre-existing** identifier — cart id, order id, or a checkout-attempt id generated on the client. Do _not_ use the session id: it is returned _by_ the create call, so it does not exist at request time. The [full example above](#full-example) uses `getCartId()` as the `Idempotency-Key` header for this reason.

## Sessions and persistence

When storage is enabled and state rehydrates with `sessionStatus === 'active'` or `'creating'`, the in-memory session (`clientSecret`) is gone — only flow state was persisted. The library detects this and downgrades to `sessionStatus: 'idle'` on hydrate, so the next `CioStripePaymentStep` mount calls `onCreateSession` again to recover.

Multi-tab session sharing (both tabs using the same clientSecret) is outside the library's scope — persist the session through a separate channel (BroadcastChannel, server-pushed WebSocket) and pass it back in.
