# Cart

The flow keeps a `cartSnapshot` in state, and it can propagate cart changes to the Stripe session via `onUpdateSession`. Merchants have three ways to feed cart data in — pick the one that matches your app's cart architecture.

## Three cart-sync APIs

**`cart` prop on `<CioPaymentProvider>`** — reactive, debounced. Best when cart lives in React state.

```tsx
const [cart, setCart] = useState<CheckoutItem[]>([]);

<CioPaymentProvider
  cart={cart}
  cartDebounceMs={400}         // default is 400ms
  onCreateSession={...}
  onUpdateSession={...}         // required for updates after creation
  ...
>
```

**`flow.setCart(items)`** — imperative, debounced. Same debounce semantics as the reactive prop; use when cart mutations come from callbacks, not renders (e.g., a recommendation carousel).

```tsx
const flow = useCheckoutFlow();
flow.setCart([...cart, newItem]);
```

**`flow.syncCart(items)`** — imperative, immediate. Bypasses the debounce and returns a promise that resolves with the updated session. Use when you need to guarantee the update is applied before proceeding.

```tsx
const flow = useCheckoutFlow();
await flow.syncCart([...cart, newItem]);
navigate('/checkout/payment');  // safe to advance
```

Content-equality check: `setCart` (and the `cart` prop) diff via JSON before scheduling a debounce, so React rerenders that emit the same items don't reset the timer.

## What happens under the hood

`onCreateSession(state)` receives the current `state.cartSnapshot` at session-create time. Any subsequent cart change is applied via `onUpdateSession({ items, reason: 'items' })`.

Updates are serialized through a queue — you can't accidentally send two overlapping `updateSession` requests. The queue drains sequentially, calling `onUpdateSession` for each patch.

If `setCart` fires *while* `onCreateSession` is still in flight, the library:

1. Stores the new items locally (`store.cartSnapshot`).
2. Waits for the create to finish.
3. Automatically flushes the pending cart via `updateSession` once the session is active.

You don't have to wire this yourself. The Stripe session ends up reflecting the *latest* cart, not the cart at create-request time.

## Cart id vs cart items

Two ways to model what your server sees:

**Send items directly.** Easiest, but you have to be sure the client-side cart is authoritative:

```tsx
onCreateSession: () =>
  fetch('/api/session', {
    method: 'POST',
    body: JSON.stringify({ items: getCart() }),
  }).then((r) => r.json());
```

**Send a cart id, let the server expand.** Cleaner for real e-commerce — the server is the source of truth. The client just tells the server which cart to price:

```tsx
onCreateSession: () =>
  fetch('/api/session', {
    method: 'POST',
    body: JSON.stringify({ cart_id: getCartId() }),
  }).then((r) => r.json());
```

If you use the cart-id pattern, you often skip the `cart` prop on the Provider entirely — the flow's `cartSnapshot` becomes redundant since the server holds the real items. Only pass `cart` if you want the flow to emit `session.updated` events with cart diffs (useful for analytics).

## Cart mutations from recommendations

A recommendation carousel (Constructor PIA-style, "Frequently bought together", etc.) firing add-to-cart while checkout is already open:

```tsx
function RecommendationCard({ item }) {
  const flow = useCheckoutFlow();
  return (
    <button onClick={() => {
      flow.syncCart([...flow.state.cartSnapshot, item]);
    }}>
      Add to cart
    </button>
  );
}
```

`syncCart` funnels through the updateSession queue, so rapid clicks don't corrupt the session — updates apply in order. The session's clientSecret survives; Stripe re-renders with the new totals.

## Debounce semantics

`cartDebounceMs` (default 400ms) sets how long to wait after the last change before flushing:

- **Faster** (`50ms`) — near-immediate sync, more network calls, jittery totals in the UI as the user increments quantity.
- **Slower** (`1000ms`) — batches burst edits, feels laggy for single edits.

Set `cartDebounceMs: 0` to disable debouncing entirely — every change flushes immediately (equivalent to `syncCart` semantics).

## Events

When cart changes propagate through `onUpdateSession`, the flow emits `session.updated`:

```ts
{
  type: 'session.updated',
  sessionId: string,
  reason: 'items',        // or 'address' / 'tax' / 'shipping' / 'coupon' / 'stock' / 'price' / 'manual'
  diff: {
    added?: CheckoutItem[],
    removed?: CheckoutItem[],
    quantityChanges?: { id: string, from: number, to: number }[],
    totalChange?: { from: number, to: number },
  }
}
```

The `diff` is computed from the previous `cartSnapshot`. Wire it to analytics:

```tsx
onEvent: (event) => {
  if (event.type === 'session.updated' && event.reason === 'items') {
    analytics.track('cart.updated', event.diff);
  }
}
```

## `CheckoutItem` shape

```ts
interface CheckoutItem {
  name: string;
  amount: number;
  quantity?: number;
  // ...additional typed fields
}
```

`name` and `amount` are required. Storage validation rejects entries without a `name`; passing an item without `amount` results in `NaN` totals downstream, so validate at the entry point.
