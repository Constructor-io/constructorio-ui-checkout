# Authentication

The checkout flow does not own auth — your app does. Two auth scenarios overlap with checkout:

1. **App-level auth** — the user clicks "Sign in" from the nav or hits a protected route.
2. **Checkout-driven auth** — the checkout flow enters an `auth` step because the user is not signed in.

Both should point at the same `/login` route and the same `<LoginPage>` component. The page decides at sign-in time which flow it is serving.

## One page, two entry paths

```tsx
// App root — CioCheckoutProvider above the router outlet
<CioCheckoutProvider
  provider="stripe"
  steps={[
    { id: 'cart', path: '/cart' },
    { id: 'auth', path: '/login' },              // routed auth step
    { id: PAYMENT_STEP, path: '/checkout/payment' },
    { id: 'done', path: '/order/confirmed' },
  ]}
  onCreateSession={createSession}
  router={router}
>
  <Routes>
    <Route path="/login" element={<LoginPage />} />
    <Route path="/cart" element={<CartPage />} />
    <Route path="/checkout/payment" element={<PaymentPage />} />
    <Route path="/order/confirmed" element={<OrderConfirmed />} />
  </Routes>
</CioCheckoutProvider>
```

## LoginPage — checkout-aware, but works standalone

```tsx
import { useCioCheckout } from '@constructor-io/constructorio-ui-checkout';
import { useNavigate, useLocation } from 'react-router-dom';

function LoginPage() {
  const flow = useCioCheckout();
  const navigate = useNavigate();
  const location = useLocation();

  const onSignedIn = () => {
    // Case A: the checkout flow entered its auth step.
    if (flow.state.currentStepId === 'auth') {
      flow.next();  // continues checkout to /checkout/payment
      return;
    }

    // Case B: normal login flow — return to the previous location.
    const state = location.state as { returnTo?: string } | null;
    const returnTo = sanitizeReturnTo(state?.returnTo);
    navigate(returnTo, { replace: true });
  };

  return <SignInForm onSignedIn={onSignedIn} />;
}
```

## Sending users to /login with a returnTo

React Router's `state` (survives a route transition, not a reload):

```tsx
<button
  onClick={() =>
    navigate('/login', { state: { returnTo: location.pathname + location.search } })
  }
>
  Sign in
</button>
```

Or with a query string (survives reloads, works with a plain `<a>`):

```tsx
<a href={`/login?returnTo=${encodeURIComponent(location.pathname)}`}>Sign in</a>
```

Then in `LoginPage`:

```tsx
const [params] = useSearchParams();
const returnTo = sanitizeReturnTo(params.get('returnTo'));
```

## Sanitizing `returnTo`

Never trust `returnTo` — an unvalidated redirect is an open-redirect vulnerability. Allow only same-origin paths:

```tsx
function sanitizeReturnTo(value: string | null | undefined): string {
  if (!value) return '/account';
  if (!value.startsWith('/')) return '/account';   // reject absolute URLs
  if (value.startsWith('//')) return '/account';   // reject protocol-relative
  if (value.includes('\\')) return '/account';     // reject backslash — browsers treat \\evil as //evil
  return value;
}
```

## Decision matrix

**User clicks "Sign in" from the nav.**
- `flow.state.currentStepId` — `null`
- After sign-in — `navigate(returnTo)`

**User hits a protected route while logged out.**
- `flow.state.currentStepId` — `null`
- After sign-in — `navigate(returnTo)` (pointed at that route)

**User starts checkout without being signed in.**
- `flow.state.currentStepId` — `'auth'` (flow pushed `/login`)
- After sign-in — `flow.next()` continues to `/checkout/payment`

**Signed-in user starts checkout.**
- `flow.state.currentStepId` — never enters auth (guard passes)
- After sign-in — n/a; flow goes straight from cart to payment

**Deep link to `/checkout/payment` while logged out.**
- `flow.state.currentStepId` — flow hydrates toward stripe, guard blocks, pushes `/login` (`currentStepId` becomes `'auth'`)
- After sign-in — `flow.next()` continues to `/checkout/payment`

## Auth-gating with guards

Guard semantics: `true` allows entry into the step; `false` blocks the transition and the flow stays on the previous step. Guards do **not** auto-skip a step when they pass.

The guard therefore belongs on the **step after auth** (the one that requires being signed in), not on the auth step itself:

```tsx
{ id: 'cart' },
{ id: 'auth', path: '/login' },
{
  id: PAYMENT_STEP,
  path: '/checkout/payment',
  guard: () => Promise.resolve(isSignedIn()),  // gates entry to payment
},
```

Behavior:
- User advances from `cart` → flow enters `auth` (routed to `/login`).
- User signs in, `LoginPage` calls `flow.next()`.
- Guard on `stripe` runs — `isSignedIn()` returns `true` → payment step entered.

A signed-in user starting checkout should not land on `/login` at all. **`optional: true` alone is not enough** — the flow does not auto-skip optional steps on entry; it only permits `next({ skip: true })` from within them. Three patterns, in order of preference:

**1. Omit the auth step from the `steps` list when you know at mount time.** Cleanest — the state machine simply has no auth step to enter.

```tsx
const authed = useIsAuthenticated();

<CioCheckoutProvider
  provider="stripe"
  steps={[
    { id: 'cart', path: '/cart' },
    ...(authed ? [] : [{ id: 'auth', path: '/login' }]),
    { id: PAYMENT_STEP, path: '/checkout/payment' },
  ]}
  ...
/>
```

Zero flash, no extra `next()` plumbing. Trade-off: the step list is snapshotted at mount, so a mid-flow logout requires remounting the provider to add the auth step back. Rare in practice — a mid-flow logout usually triggers a full navigation anyway.

**2. Auto-advance from within the auth step.** For cases where auth state resolves asynchronously after mount:

```tsx
function AuthStepBody() {
  const flow = useCioCheckout();
  useEffect(() => {
    if (isSignedIn()) flow.next();
  }, [flow.next]);
  return isSignedIn() ? null : <SignInForm />;
}

<CioCheckoutStep id="auth"><AuthStepBody /></CioCheckoutStep>
```

Brief render of `null` before the transition. Add a loading state if the flash is visible.

**3. Skip via `next({ skip: true })` from the previous step.** Requires marking `auth` as `optional`:

```tsx
{ id: 'auth', path: '/login', optional: true },

// From the cart step's Next button:
if (isSignedIn()) {
  flow.next({ skip: true });   // jumps past auth
} else {
  flow.next();                 // enters auth
}
```

Splits the auth decision across the previous step — awkward when multiple steps can precede auth. Prefer 1 or 2.

`isSignedIn()` is a plain function reading your auth store, cookie, or token — no context needed.

## Modal instead of routed page

To present sign-in as a modal over the current page (no URL change), give the auth step no `path` and apply the same auto-advance / skip pattern:

```tsx
{ id: 'auth' }
```

Render a `<SignInModal>` inside `<CioCheckoutStep id="auth">`. The modal appears only during checkout; `<LoginPage>` at `/login` still handles the nav-triggered case. Trade-offs: no deep link to auth and no browser-back into auth, but no route change either.

## Multi-step auth (OTP, 2FA, passkey, MFA)

The checkout flow does not care about the auth *strategy* — only about the answer to "is the user signed in yet?" A credentials → OTP → verified sequence happens entirely inside `LoginPage`. Only the final success handler calls `flow.next()`.

```tsx
function LoginPage() {
  const flow = useCioCheckout();
  const navigate = useNavigate();
  const location = useLocation();

  const onFullySignedIn = () => {
    if (flow.state.currentStepId === 'auth') {
      flow.next();  // one call, at the very end of the auth wizard
      return;
    }
    const returnTo = sanitizeReturnTo(
      (location.state as { returnTo?: string } | null)?.returnTo
    );
    navigate(returnTo, { replace: true });
  };

  return <AuthWizard onSuccess={onFullySignedIn} />;
}

function AuthWizard({ onSuccess }: { onSuccess: () => void }) {
  const [step, setStep] = useState<'credentials' | 'otp'>('credentials');
  const [challenge, setChallenge] = useState<OtpChallenge | null>(null);

  if (step === 'credentials') {
    return (
      <CredentialsForm
        onChallenge={(c) => {
          setChallenge(c);
          setStep('otp');
        }}
      />
    );
  }
  return <OtpForm challenge={challenge!} onVerified={onSuccess} />;
}
```

`isSignedIn()` (the value the checkout guard reads) returns `true` only once the *final* verification succeeds — not when the user submits credentials and receives an OTP challenge.

### Do the OTP substeps need URLs of their own?

**No** — keep OTP as internal component state (the code above). Simplest. Users cannot refresh into a mid-OTP screen, and you cannot deep-link into a half-completed auth flow, which is typically the desired security posture.

**Yes** — nest routes *inside* the auth entry route. The checkout `auth` step still owns `/login` as its entry; sub-URLs like `/login/verify` live under the same checkout step:

```tsx
<Route path="/login" element={<LoginPage />}>
  <Route index element={<CredentialsForm />} />
  <Route path="verify" element={<OtpForm />} />
</Route>
```

`LoginPage` renders `<Outlet />` and handles the final `onSuccess`. From the checkout flow's perspective, `currentStepId` stays `'auth'` throughout — no reconfiguration needed.

### Don't split auth into multiple checkout steps

Tempting anti-pattern:

```tsx
// DON'T
steps={[
  { id: 'cart', path: '/cart' },
  { id: 'auth-credentials', path: '/login' },
  { id: 'auth-otp', path: '/login/verify' },
  { id: PAYMENT_STEP, path: '/checkout/payment' },
]}
```

This bakes the auth strategy into the checkout state machine. Adding SSO, passkey, or step-up MFA later requires churning the checkout config every time. Keep the checkout flow at a single `auth` gate — auth owns its own internals.
